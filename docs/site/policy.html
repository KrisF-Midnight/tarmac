Chapter 3

Policy

Rules over three kinds of source, enforced in two places and proven two ways — unit tests on one side, a live refusal on the other.

Moving parts

conftest evaluates Rego over files before a merge. In the cluster it is Kubernetes’ own ValidatingAdmissionPolicy, written in CEL — no Gatekeeper, no Kyverno.

Subject

Source, not results: Terraform, the Kubernetes manifests that declare what runs, and the Dockerfile. No plan is parsed — a later gate checks what the provider accepts.

Enforcement point

Both. conftest runs rules written in Rego, a policy language, over files before a merge; the API server checks objects at admission, before accepting them.

Authority

Anyone who merges without CI bypasses the first check. The second cannot be, and it follows kubectl debug onto the ephemeral-container endpoint rather than stopping at the Pod.

Rule tests

115 tests run the Rego against sample inputs; 35 more evaluate the admission CEL with no cluster running. Installation still waits for a real refusal per policy, so a dead rule cannot hide behind a live one.

Scope & exemptions

Scope is an exclusion list, not opt-in: the admission bindings skip six named namespaces — cluster partitions — only two of them the platform’s own.

Known gap

Only one of the two policies can follow. Kubernetes refuses any request that sets resources on an ephemeral container, so a rule demanding limits there would ban debugging rather than police it — and debug containers go on consuming capacity that nothing accounts for.

Where to look
  • tarmac/policy/kubernetes/ — the manifest rules, each with its own test file
  • tarmac/policy/terraform/ — five more, read straight off the HCL
  • tarmac/policy/dockerfile/ — the only rules that read a Dockerfile, and the one image no manifest rule can see
  • tarmac/policy/admission/ — the two the API server enforces, and the namespaces it skips
  • tarmac/scripts/admission-up.sh — installs, then waits to watch both refusals
